# Comparativo com banco relacional (aproximadamente meia página)

Para o caso demonstrado, o DynamoDB facilita o acesso rápido a um carrinho específico porque todos os seus itens estão agrupados sob a mesma chave de partição (`PK = CART#<id>`). Uma operação de `Query` retorna os itens sem precisar combinar tabelas. Também é simples buscar um produto específico com a chave completa, usando `GetItem`. Esse formato combina com aplicações em que a maior parte das operações começa identificando um carrinho. A modelagem prioriza os padrões de consulta, em vez da normalização dos dados.

No modelo relacional, o mesmo problema pode ser representado por três tabelas: `carrinhos`, `produtos` e `itens_carrinho`. Essa solução evita repetir informações do catálogo e permite impor chaves estrangeiras. Por outro lado, para mostrar os itens de um carrinho com os nomes e preços dos produtos, é necessário um `JOIN`. Para calcular o total, o SQL possui `SUM`, o que é conveniente; na solução demonstrada com DynamoDB, o total é calculado pelo JavaScript depois da consulta. Se houver relatórios complexos sobre várias compras, o banco SQL costuma ser mais simples.

Assim, **para acessar e modificar carrinhos individuais com chaves conhecidas, o DynamoDB é uma boa escolha**. Entretanto, **para um projeto pequeno que exige relações e consultas analíticas, um banco SQL também pode ser a melhor opção**. A escolha depende do tipo de consulta, da escala e da necessidade de consistência e manutenção. O DynamoDB Local serve à demonstração da estrutura chave-valor, mas não apaga itens automaticamente ao vencer o TTL; esse comportamento é oferecido pelo serviço DynamoDB na AWS de forma assíncrona.
